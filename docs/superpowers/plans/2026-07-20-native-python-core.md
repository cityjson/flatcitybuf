# Native Python FlatCityBuf Core — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the PyO3 extension in `src/rust/fcb_py` with a from-scratch pure-Python implementation of the FlatCityBuf **reader** (local files + HTTP range access, sequential scan, spatial and attribute queries, CityJSON emission), with no Rust at build or run time.

**Architecture:** A `py3-none-any` wheel with no compiled code. FlatBuffers tables are read through flatc-generated Python plus the pure-Python `flatbuffers` runtime; the R-tree and B+tree sections are raw little-endian structs read directly with `struct`/`memoryview`, never through FlatBuffers. I/O sits behind a `RangeReader` protocol so local files, HTTP and test doubles are interchangeable — the same shape the C++ reader uses. numpy is an optional extra used only for bulk vertex decoding.

**Tech Stack:** Python ≥3.9, `flatbuffers` (pure-Python runtime), stdlib `struct`/`urllib`/`dataclasses`; pytest, ruff, mypy (strict); optional extras `numpy` (bulk paths) and `httpx` (async HTTP).

## READ THIS FIRST

### Two reference implementations already exist. Use them.

This is the **third** implementation of this reader. Rust (`src/rust/fcb_core`) is the origin; C++ (`src/cpp`) was ported from it in July 2026 and is fully conformant. That means:

1. **The format is already documented to ground truth.** `docs/superpowers/plans/2026-07-19-native-cpp-core.md` lines 37-170 hold a "Format Reference" with every constant, formula and byte offset **cited to the Rust source line that proves it**: file layout, feature framing, packed R-tree, attribute B+tree, all seven key encodings, operator lowering, HTTP constants. **Read that section before writing any code, and cite it from your tests instead of re-deriving anything.** This plan does not duplicate it.
2. **The deliberate divergences are already decided** (same document, "Known divergences from the Rust reader"): `Byte` columns decode as `u8` (matching the writer, not Rust's reader), `Json`/`Binary` index queries are rejected, float `max_value()` is `+inf` so NaN-keyed features are invisible to range queries, `DateTime` `min_value()` is epoch 0 so pre-1970 timestamps are invisible to `Le`/`Ne`. **Python must make the same four choices**, so all three implementations agree.
3. **The conformance corpus exists** and is generated by the Rust CLI acting as oracle (`scripts/gen_conformance.sh`). Task 2 moves it somewhere all three implementations can share.
4. **Eight upstream defects found during the C++ port are written up** in `docs/upstream-findings.md`. Findings #7 and #8 matter most here: appearance indices must serialize as `1`/`null`, never `[1]`/`[]`, and two appearance shapes used to lose a nesting level. Python must land on the fixed side of both — the corpus already encodes the correct answers.

### The single most important lesson from the C++ port

Both round-trip bugs in finding #8 survived because every test compared the new reader against the reference reader's *output*, and both agreed on the wrong answer. **Comparing against the corpus is necessary but not sufficient.** Where Python decodes something the corpus does not exercise, write a round-trip test that goes through the Rust *writer*. `geom_temp`, for instance, exercises neither of the two branches that were broken.

### The oracle technique (use it, do not hand-derive expected values)

When you need to know what the reference does for some input, make the reference tell you: temporarily add a test to the Rust source that prints the actual output for each case, run it, pin those values in the Python tests, revert the injection. This caught a wrong hand-derivation during the C++ port. `src/rust/fcb_core/src/reader/geom_decoder.rs` is where the appearance decoders live.

### Conventions

- **TDD, strictly.** Write the failing test, run it, confirm it fails *for the expected reason*, implement, confirm it passes, commit. Steps below that say "verify it fails" are not optional.
- **Fable for hard analytical passes.** `Agent` tool with `model: "fable"`. Give it one narrow question, forbid behaviour changes, demand evidence (printed byte arrays, side-by-side JSON) rather than conclusions. It produced the branch-condition spec that made the C++ appearance port correct on the first try, and the round-trip investigation that classified four suspected bugs into two real and two unreachable.
- **codex review before closing each stage:** `codex exec --model gpt-5.6-sol --sandbox read-only "<focused prompt>"`. Three real defects, zero false positives, during the C++ port.
- Commit after every task. Never leave a red suite.

### Python-specific gotchas that will bite

These have no C++ analogue, so nothing in the existing ports warns about them:

1. **Optional scalars are invisible in generated Python.** `MaterialMapping.value` is `uint = null` in `src/fbs/geometry.fbs`. C++ gets `flatbuffers::Optional<uint32_t>`; the Python generator returns the *default* (0) when the field is absent, so "shared material 0" and "no shared material" look identical. You must test the vtable directly:
   ```python
   def _field_present(tab: flatbuffers.table.Table, vtable_offset: int) -> bool:
       return tab.Offset(vtable_offset) != 0
   ```
   The same applies to `SemanticObject.parent`, `Texture.wrap_mode`, `Texture.texture_type`, `Material.ambient_intensity`/`shininess`/`transparency`/`is_smooth`. Getting this wrong silently invents data. Task 8 pins it with a test.
2. **`u32::MAX` (4294967295) means null**, in semantics values and in appearance index arrays. Python has no unsigned overflow to make this obvious — it will happily emit `4294967295` into your JSON.
3. **Python ints are arbitrary precision.** Signed values must be decoded with the right `struct` format (`<q` vs `<Q`), not fixed up afterwards. A `u64` offset read as `<q` becomes negative past 2^63 and indexes backwards.
4. **Float key ordering is `ordered_float`, not Python's.** NaN sorts *greatest*, `NaN == NaN` is true, `-0.0 == +0.0`. Python's `sort` puts NaN wherever it lands and `float('nan') != float('nan')`. Implement an explicit comparator; do not use `<`.
5. **Fixed-width string keys are truncated at the BYTE level and can split a UTF-8 sequence.** Compare on raw `bytes`, never on `str`. Only decode for display, with `errors="replace"`.
6. **Size-prefixed FlatBuffers roots.** The Python runtime's API for this has changed across versions. Verify what your pinned `flatbuffers` provides (`GetSizePrefixedRootAs*` vs passing `offset=4`) with a test against a real `.fcb` before building on it — do not assume.
7. **Alignment does not apply.** The C++ port needed `memcpy` for misaligned structs; Python's `struct.unpack_from` has no alignment requirement. Ignore every alignment note in the C++ sources.

## Task 5: RangeReader protocol, file adapter, buffered decorator

**Files:** Create `src/py/flatcitybuf/range_reader.py`, `src/py/tests/test_range_reader.py`

**Interfaces:**
- Produces:

  class RangeReader(Protocol):
      def read(self, offset: int, length: int) -> bytes: ...
      def total_size(self) -> int: ...

class CountingReader:
    def __init__(self, data: bytes) -> None:
        self.data, self.reads = data, []
    def read(self, offset: int, length: int) -> bytes:
        self.reads.append((offset, length))
        return self.data[offset : offset + length]
    def total_size(self) -> int:
        return len(self.data)

    assert r.read(4, 4) == bytes(range(4, 8))

def test_read_past_end_raises() -> None:

## Task 8: CityJSON emission — boundaries, semantics, appearance, templates

**Files:** Create `src/py/flatcitybuf/geometry.py`, `src/py/flatcitybuf/cityjson.py`; tests `test_geometry.py`

**Interfaces:**
- Produces: `decode_boundaries(solids, shells, surfaces, strings, indices) -> list`; `decode_material_values(...)`, `decode_texture_values(...)`; `to_cityjson_metadata(header) -> dict`; `to_cityjson_feature(feature, header) -> dict`.

Port from `src/cpp/src/geometry.cpp` and `src/cpp/src/cityjson.cpp` — the C++ versions are current, including finding #8's fixes. Rules that are easy to get subtly wrong:

- **Collapse applies only at the OUTERMOST level.** Inner levels always wrap. Getting this backwards produces output one level off that still looks structurally plausible.
- **`u32::MAX` → `None`** (JSON `null`) in semantics values and in both appearance index arrays.
- **A single Solid drops the solid level; so does `solids == [1]`.** That second half is finding #8 — do not reintroduce a `solids[0] > 1` guard.
- **A single-string MultiLineString keeps its depth** — no `len(strings) > 1` guard.
- **An empty (as opposed to absent) material/texture mapping vector omits the key entirely**; only a vector whose mappings were all skipped yields `{}`. The `empty_appearance` fixture covers this.
- **Per-feature `appearance`** (materials, textures, `vertices-texture`) must be emitted — C++ forgot it initially and the conformance test did not catch it because it compared only selected keys.
