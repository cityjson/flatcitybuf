# citygml-tools cross-check corpus

Real CityGML, and what the reference implementation makes of it.

Each sample is a pair:

| file | what it is |
|---|---|
| `<name>.gml` | the CityGML input, verbatim from its source (cut down, never edited) |
| `<name>.citygml-tools.city.json` | the CityJSON 2.0 that **citygml-tools** produces from it |

`tests/xcheck.rs` converts each `.gml` with `parse_citygml` and holds the
result against the reference structurally — same objects, same types, same
nesting, same attributes, same geometries per LoD, same semantics per polygon,
same corners in the real world, same appearance palette. It does **not** compare
byte for byte: two correct converters do not agree byte for byte, and every
place the two legitimately differ is a named constant in that file with the
reason.

The reference outputs are committed so that the suite needs no Java, no network
and no citygml-tools to run.

## What each sample is for

- **`fzk-haus-lod2`** — CityGML 2.0. One `bldg:Building`, LoD 2, whose
  `bldg:lod2Solid` is assembled by `xlink` from the polygons written under its
  seven `bldg:boundedBy` surfaces. `gen:stringAttribute`, `gen:dateAttribute`
  and `gen:measureAttribute`, `bldg:measuredHeight`, `bldg:storeys*`, and an
  `xAL` address. The mandatory case: LoD 2 with semantic surfaces.
- **`railway-lod3`** — CityGML 2.0, and the breadth sample. Eight members
  covering seven modules: `bldg:Building` (with two
  `bldg:outerBuildingInstallation`s and `bldg:Door`/`bldg:Window` openings),
  `tun:Tunnel` (with two `tun:TunnelInstallation`s), two `brid:Bridge`es,
  `veg:SolitaryVegetationObject` (a `core:ImplicitGeometry` with its template
  in the same member), `frn:CityFurniture`, `gen:GenericCityObject` and
  `tran:Railway`. Appearance throughout: `app:X3DMaterial` and
  `app:ParameterizedTexture` with `app:TexCoordList`.
- **`denhaag-lod2`** — CityGML **1.0**, and the volume sample: 25 members that
  become 107 City Objects, 90 of them LoD 2 solids with semantics. Every object
  carries its own `app:appearance` rather than the `CityModel` carrying an
  `app:appearanceMember`, and the file begins with a UTF-8 BOM. This is the
  sample that shows the 1.0 namespaces are read.

## Regenerating

Nothing here is generated by this crate, and nothing here needs regenerating
unless a sample changes. If one does:

**1. citygml-tools.** Version **2.5.0**, run on **OpenJDK 21.0.11**. Download
outside the repository:

```sh
cd "$SCRATCH"
curl -sSLO https://github.com/citygml4j/citygml-tools/releases/download/v2.5.0/citygml-tools-2.5.0.zip
unzip -q citygml-tools-2.5.0.zip
```

**2. The inputs.** Download the source file from the URL in the table above.
`fzk-haus-lod2.gml` is that file unchanged. The other two are cut down by
`cut_down.py` in this directory, which copies the XML prolog, the root start
tag, `gml:boundedBy` and the selected top-level `cityObjectMember`s **verbatim**
— so the kept members are byte-identical to the original — and keeps an
`app:appearanceMember` only when every `app:target` it names resolves inside
those members:

```sh
python3 cut_down.py "$SCRATCH/LoD3_Railway.gml" railway-lod3.gml 0,19,20,22,32,38,47,50
python3 cut_down.py "$SCRATCH/DenHaag_01.xml"   denhaag-lod2.gml 1-25
```

The member indices are 0-based positions in the source document. The railway's
are a hand-picked spread over its modules; Den Haag's skip member 0, a 1.8 MB
`dem:ReliefFeature`, and take the buildings that follow.

**3. The reference outputs.**

```sh
"$SCRATCH/citygml-tools-2.5.0/citygml-tools" to-cityjson \
    --cityjson-version=2.0 --replace-templates <name>.gml
mv <name>.json <name>.citygml-tools.city.json
```

`--replace-templates` is not optional. Without it citygml-tools writes a
`core:ImplicitGeometry` as a CityJSON `GeometryInstance` pointing into a
document-level `geometry-templates` array, while this converter flattens the
template into real coordinates where it stands. Both are valid CityJSON and
they are not comparable; the flag makes citygml-tools flatten too, so that the
comparison is about the geometry rather than about which of the two
representations each side chose. It changes nothing in a file with no implicit
geometry.

Everything else is left at its default, in particular `--vertex-precision=3`
(millimetres), which is the scale `ParseOptions::default()` quantises at.
